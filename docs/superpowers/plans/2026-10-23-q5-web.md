# Q5-web plan: HMS, firmware, diagnostics, info, discovery UI

Depends on PR #20 (q5-backend). API mocked in tests; contract = backend `schemas/printer_ops.py`.

## Contract (as shipped by backend)
- `GET /printers/{id}/hms` -> HmsFault[] (code, full_code, kind, severity, module, description|null, wiki_url, actions[])
- `POST /printers/{id}/hms/clear`; `POST .../hms/action` {print_error, action}
- `GET /printers/{id}/firmware` -> {model_supported, current, latest, release_notes, update_available, download_available, upload}
- `POST /printers/{id}/firmware/upload` (409 = nothing to stage)
- `POST /printers/diagnostic` {host, serial, access_code, model?}; `GET /printers/{id}/diagnostic` -> {ok, checks[{id,status,hint}]}
- `POST /printers/discover` {cidr?} -> [{host, serial, model_hint, source}]
Deviation from spec wording: check key is `id` (not `name`), notes key is `release_notes`.

## Tasks
1. `web/src/api/types.ts`: Q1/Q5 types (capabilities, status hms/firmware/dev_mode, Q5 payloads), all optional on existing types.
2. `web/src/api/printerOps.ts`: hooks (useHms/Clear/Action, useFirmware/Upload, useDiagnostic, useDiscover).
3. `components/print/modals/`: HmsModal, FirmwareModal, DiagnosticModal (+ DiagnosticChecks), PrinterInfoModal, `usePrinterModals(printerId)` hook, index.
4. `PrinterDetailPage`: Info / HMS (n, only when non-empty) / Firmware / Diagnose row (Q3 will restructure).
5. `PrinterSetupCard`: Discover section (subnet defaults to first printer's /24), click-to-fill; "Run diagnostic"; preflight on add with Back / Save anyway (preflight request error never blocks).
6. Tests: modals.test.tsx, PrinterSetupCard.test.tsx additions.
